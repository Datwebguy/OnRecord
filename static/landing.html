01 / FAILURE MODE

Why Unfiled Work Collapses

Incoming work dies when the acting agent “remembers” a chat that was never filed.

Most multi-agent systems rely on loose conversational memory: one model promises to do something in a prompt window, context drifts, and an action model hallucinates context that never existed in storage. Irreversible steps get executed on unverified assumptions.

CHAT-BOUND AGENTS (FLAWED)

Shared context window. The executing agent acts on conversational suggestions, untracked chat tokens, and unverified assumptions. No durable paper trail.

ONRECORD DESK (ISOLATED)

Scout writes WARM records and COLD events. Clerk reads only what was filed into the journal. If an entity was never filed, Clerk returns NOT ON RECORD and refuses to act.

02 / INTERFACE

Three Columns. Not Two Chat Toys.

Scout

Filing Role

Reads only the allowlisted sources saved in Scene by the operator. Discovers and files incoming asks and people directly into memory.

Scout has no wallet, cannot ping, cannot spend, and never writes action decisions.

Queue

Filed Backlog

The Queue is not a separate database table. It is dynamically projected from memory: filed tasks that have no corresponding action recorded yet.

Zero cached state. If memory is deleted, the queue reflects it instantly.

Clerk

Action Role

Opens only filed tasks. Queries memory for the person and ask records. Evaluates and applies explicit stamps:

ON RECORD SKIP NOT ON RECORD

Proposes onchain pings only if a verified wallet exists, requiring explicit operator confirmation.

03 / EXECUTION PIPELINE

How It Works

01 / SCENE

Operator Allowlist

Scene starts empty. You paste the exact repositories or Base wallets to watch. If Scene is empty, Scout files nothing.

02 / FILE

Scout Writes Files

Scout processes sources, sets WARM entities (Person, Ask), and logs an append-only COLD filed event.

03 / RECALL

Clerk Reads Only

New process starts. Clerk reads the COLD stream. If a name was never filed, Clerk stamps NOT ON RECORD and halts.

04 / SETTLE

Confirmed Base Ping

Clerk proposes an onchain ping to Person.bound on Base. Transaction broadcasts only after you check confirm.

04 / ARCHITECTURE

A Desk Anyone Can Run

OnRecord is a self-contained incoming work desk. One operator runs two isolated roles across a single database file with partitioned tenant memory.

You bring the real GitHub repository or Base wallet address. The system ships without seed fixtures, preloaded personas, or fake demo rows.

DESK INVARIANTS

  • Scout writes only tenant_scout
  • Clerk writes only tenant_clerk
  • Clerk reads tenant_scout for filings; miss = stop
  • Irreversible Base action requires human confirmation
  • Dynamic queue projection with zero secondary tables
05 / VERIFICATION

Frequently Asked Questions

What is Scene?

The allowlist you paste at runtime. Empty sources means Scout files nothing and the queue remains empty.

Can Clerk invent a person?

No. If an entity is not found in Scout's memory partition, Clerk immediately returns NOT ON RECORD.

Does Scout spend?

No. Scout has no wallet, has no private key, and never signs transactions.

What is a ping?

One operator-confirmed Base mainnet transaction to a bound address that Scout filed from the Scene.

Is there demo data?

No. No preloaded profiles, mock asks, hardcoded wallets, or fake hashes exist in the codebase.
